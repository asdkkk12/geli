# 同类项目部署方案

## 1. 目标和基本判断

假设学校服务器上已经部署 `geli` 平台，另有一个功能和技术栈相近的项目，以下简称“目标项目”。目标项目可以通过本平台以受控应用的方式部署到用户容器中。

需要先区分两种情况：

| 情况 | 部署方式 | 是否推荐放进普通用户容器 |
| --- | --- | --- |
| 目标项目是普通 Web/后端业务应用 | 制作审核镜像，注册为平台镜像模板 | 可以 |
| 目标项目本身也是完整的容器管理平台 | 单独部署一套控制面和 Agent | 不可以直接嵌套 |

本方案推荐第一种方式。普通用户容器不提供 Docker CLI、Docker Socket 或 privileged 权限，不能在容器中再创建和管理 Docker 容器。

## 2. 推荐架构：目标项目作为平台应用

```text
用户浏览器
    │
    ▼
geli 管理节点
    ├── Web / API / PostgreSQL / Redis / Traefik
    └── Agent（通过签名请求管理容器）
            │
            ▼
      目标项目容器
        ├── 目标项目 Web/API 进程
        ├── 独立网络
        ├── 受限 CPU、内存和磁盘
        ├── 用户数据卷
        └── 审批后的应用端口
```

平台负责用户、申请、审批、资源分配、容器生命周期、终端和应用入口；目标项目只负责自己的业务代码和运行时。

## 3. 部署前准备

### 3.1 明确目标项目运行方式

确认以下内容：

- 启动命令，例如 `npm run start`、`java -jar app.jar` 或 `python app.py`；
- 对外提供服务的内部端口，例如 `8080`；
- 是否需要 PostgreSQL、Redis、对象存储或其他外部服务；
- 需要的 Node.js、Python、Java 版本；
- 是否需要编译步骤；
- 是否需要持久化目录；
- 是否需要环境变量和密钥；
- 是否允许访问互联网或校内其他服务。

目标项目应监听：

```text
0.0.0.0:<申请的内部端口>
```

不能只监听容器内的 `127.0.0.1`，否则平台网关无法访问。

### 3.2 准备生产存储

生产环境不能使用本机演示中的 `tmpfs` 作为用户工作盘。应选择支持容量限制和持久化的 Docker Volume 驱动，并验证：

1. 超过审批容量时写入会失败；
2. 容器停止后数据仍在；
3. 容器重建后数据仍能恢复；
4. 删除容器和删除卷是两个独立操作；
5. 数据库和用户代码都有独立备份。

### 3.3 准备镜像仓库

镜像应由管理员构建、审核和发布。不要允许用户在申请时提交任意镜像地址。

镜像发布可以使用校内 Registry：

```text
registry.school.edu/lab/target-project:1.0.0
```

生产环境建议在平台模板中使用镜像 digest，而不是只使用可变的 `latest` 标签。

## 4. 制作目标项目镜像

示例：Node.js 项目：

```dockerfile
FROM node:22-bookworm-slim

WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .

ENV NODE_ENV=production
EXPOSE 8080
USER 1000:1000
CMD ["npm", "run", "start"]
```

构建和测试：

```bash
docker build -t registry.school.edu/lab/target-project:1.0.0 .
docker run --rm -p 18080:8080 registry.school.edu/lab/target-project:1.0.0
curl http://127.0.0.1:18080/health
docker push registry.school.edu/lab/target-project:1.0.0
```

镜像至少应满足：

- 非 root 用户运行；
- 提供明确的健康检查接口；
- 不包含密钥、Token、证书私钥或生产数据库密码；
- 不自动运行 Docker；
- 不需要 `sudo`、`privileged` 或 Docker Socket；
- 日志输出到标准输出和标准错误；
- 应用监听 `0.0.0.0`；
- 使用固定版本依赖；
- 经过漏洞扫描和启动测试。

## 5. 注册为 geli 镜像模板

在管理节点和每个 Agent 节点配置相同的镜像模板映射：

```json
{
  "target-project": "registry.school.edu/lab/target-project@sha256:<digest>"
}
```

对应环境变量：

```text
IMAGE_TEMPLATES_JSON
```

Agent 必须预先加载或能够安全访问该镜像。平台只接受配置中已审核的模板，不接受用户直接提交未经审核的镜像名。

同时在管理节点配置服务器资源：

```json
[
  {
    "id": "server-a",
    "url": "https://agent-a.school.edu:3100",
    "secretEnv": "AGENT_A_SECRET",
    "cpu": 12,
    "memoryMb": 24576,
    "diskGb": 500
  }
]
```

生产环境还应配置：

- `NODE_ENV=production`；
- `PUBLIC_ORIGIN`；
- `APP_DOMAIN`；
- `GATEWAY_TOKEN`；
- Agent TLS 证书；
- API 与 Agent 之间的独立 HMAC 密钥；
- 支持硬容量限制的 `VOLUME_DRIVER` 和 `VOLUME_OPTIONS_JSON`。

## 6. 用户申请和平台创建流程

用户在 Web 页面填写：

- 容器名称；
- 用途；
- 镜像模板 `target-project`；
- CPU；
- 内存；
- 磁盘；
- 运行时长；
- 应用内部端口，例如 `8080`。

平台处理流程：

```text
用户提交申请
  → PostgreSQL 写入 applications
  → 审批人审核
  → PostgreSQL 写入 containers 和 tasks
  → BullMQ 投递创建任务
  → API 通过 HMAC/TLS 调用 Agent
  → Agent 创建独立网络、数据卷和容器
  → Agent 发布已审批端口
  → API 更新容器状态
  → 网关刷新应用路由
```

用户不直接执行 `docker run`，也不直接指定任意宿主机端口、网络或卷。

## 7. 目标项目需要数据库时

不要在普通用户容器中再启动 PostgreSQL 或 Redis Docker 容器。推荐以下方式：

### 方案 A：学校统一数据库

- 为目标项目创建独立数据库和账号；
- 使用独立 Schema 或独立数据库名；
- 通过密钥系统注入连接串；
- 只允许目标项目容器网段访问；
- 定期备份和恢复演练。

### 方案 B：平台节点上的专用服务

- 由管理员单独部署 PostgreSQL/Redis；
- 不与平台核心数据库共用账号；
- 设置独立端口、账号和权限；
- 不允许用户直接访问数据库管理接口。

环境变量示例：

```text
DATABASE_URL=postgresql://target_user:<secret>@db.school.edu:5432/target_project
REDIS_URL=rediss://:<secret>@redis.school.edu:6380/target_project
```

真实密码应通过密钥系统或服务管理器注入，不能写进镜像或提交到 Git。

## 8. 应用入口和域名

目标项目启动后监听容器内部端口，例如：

```bash
npm run start -- --host 0.0.0.0 --port 8080
```

平台会为容器映射动态宿主机端口，网关再将域名转发到该端口：

```text
https://c-<container-id>.apps.school.edu
        ↓
Traefik / Nginx
        ↓
server-a 管理网地址:动态端口
        ↓
目标项目容器:8080
```

需要配置：

- `*.apps.school.edu` 泛域名 DNS；
- 网关 HTTPS 证书；
- 网关到 Agent 节点的管理网络连通性；
- 防火墙只允许网关访问应用端口；
- 不允许用户绕过网关直接访问动态端口。

## 9. 如果目标项目本身也是 geli 的副本

如果“几乎完全相同”指的是另一套完整的平台，而不是普通业务应用，则不能按普通用户容器部署。

应采用独立控制面方案：

```text
学校平台 A
  ├── API A / Agent A / DB A / Redis A
  └── 管理域名 A

学校平台 B
  ├── API B / Agent B / DB B / Redis B
  └── 管理域名 B
```

平台 B 应具有：

- 独立 PostgreSQL 数据库；
- 独立 Redis；
- 独立 Agent 密钥；
- 独立 TLS 证书；
- 独立域名和网关路由；
- 独立 Docker 节点或明确的资源边界；
- 独立备份和审计数据。

平台 A 可以把平台 B 当成一个被审核的应用入口，但不能把平台 B 的 Docker Socket 暴露给普通用户容器。

## 10. 升级、回滚和数据保护

目标项目升级建议采用不可变镜像：

```text
target-project:1.0.0 → target-project:1.1.0
```

流程：

1. 构建新镜像；
2. 扫描漏洞并进行功能测试；
3. 在测试容器中验证健康检查、数据库迁移和端口；
4. 更新平台模板映射；
5. 新申请使用新版本；
6. 已运行容器按变更计划重建或滚动迁移；
7. 观察日志、错误率和资源使用；
8. 出现问题时恢复旧 digest。

数据库迁移必须可回滚或提供备份恢复方案。升级镜像不能直接删除旧数据卷。

## 11. 安全和验收清单

上线前至少验证：

- 普通用户只能访问自己的容器；
- 普通用户不能访问 Docker Socket；
- 普通用户不能执行宿主机命令；
- 普通用户不能访问其他项目数据库；
- 目标项目容器不是 privileged；
- 容器以非 root 用户运行；
- 目标端口只能通过网关访问；
- 镜像来源已审核且使用固定版本或 digest；
- 资源超限时创建被拒绝或受到限制；
- 容器过期后自动停止并撤销入口；
- 删除容器和删除数据卷有明确的权限区分；
- PostgreSQL、Redis、用户数据卷都有备份策略；
- API 与 Agent 的 TLS 和 HMAC 校验有效；
- 日志和审计记录不包含密码、Token 或私钥。

## 12. 最终建议

最安全、最符合本项目设计的方案是：

1. 将目标项目制作成管理员审核的 Docker 镜像；
2. 在 `IMAGE_TEMPLATES_JSON` 中注册镜像模板；
3. 让用户通过申请和审批流程创建目标项目容器；
4. 使用独立数据库、Redis 和持久化卷；
5. 通过 Traefik/Nginx 提供域名入口；
6. 通过 Agent 统一执行容器生命周期管理；
7. 不在用户容器中嵌套 Docker，也不暴露 Docker Socket；
8. 如果目标项目本身是完整平台，则单独部署一套控制面。
